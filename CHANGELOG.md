## [Unreleased]

### Added

- **`demo-quickstart.sh` now checks that the operational schema exists before it seeds, and the First-5-Minutes path restores the dump first.** A clean clone has no operational schema to build from: the tracked `metadata/` tree is a partial overlay (13 of the running instance's 32 `entityDefs` — see `metadata/README.md`), so `location`, `service_provider`, `site_visit`, `service_area`, `finding` and the rest come from a provisioned `atrocore.dump`, not from the repository. Restoring it is now step 5 of the README checklist (before the metadata install), the synthetic-dataset section says it loads *on top of* a provisioned instance, runbook §7.2 carries the same warning, and the quickstart's preflight probes `public.service_area` and stops with the exact restore command instead of failing four steps later inside a seed script (`SCHEMA_PROBE_TABLE` overrides the probe so the failure path can be exercised deliberately). Reproduced on an isolated fresh instance: without the dump the app serves after bootstrap but `seed-usoap-vocabularies.sh` fails with `column "multilingual" of relation "extensible_enum" does not exist` and `seed-demo-dataset.sh` with `relation "public.service_area" does not exist`. The underlying metadata gap is scheduled as **P2.6** in `TECHNICAL_DEBT_ANALYSIS.md`.
- **The compliance integration runbook and its executable demo quickstart now live in this repository.** `docs/COMPLIANCE_INTEGRATION_RUNBOOK.md` (previously at the workspace root, outside every repository and therefore unversioned) and `scripts/demo-quickstart.sh` (re-rooted here) moved into the repository a newcomer has to start from. The script takes a running stack to the seeded demo dataset, the demo identities, the imported work products and the read-only verification in one additive, idempotent pass, then prints the closure-review calls it deliberately leaves to a human; §7 of the runbook remains the step-by-step version and §7.7 the traps. Every other repository's README now links to §7, so the sequence is documented once instead of per repository. Verified by running the moved script from its new home (`--skip-seed --skip-import`) and by re-reading the runbook's relative references.
- **The demo dataset now includes a checklist catalog and its USOAP citation chain.** Three topics and nine questions across the demo specialties (`ATS-9001…9003`, `NAV-…`, `MET-…` — the `9xxx` range, because `code` is unique per `(code, deleted)` and the low ranges are taken by the operational catalog), each cited through `Normativa → AcapiteOACI → UsoapProtocolQuestion` with synthetic `PQ 99.x` codes (the entity's own pattern requires `PQ N.NNN`, and ICAO does not assign 99.x). It also seeds `InspectionQuestion`, the per-inspection selection `/checklist` actually queries — the master catalog alone is invisible to the app. Verified against the running stack: `/checklist` now returns the three ATS questions with the topic, verification, guidance, `reglamento`/`articulo`/`texto`, ICAO reference and a resolved `usoapPqReference` (`CE-5`, `PQ 99.001`), and `riskLevel` resolving to `Medium`/`Low`/`High` — all labels coming from the vocabulary seed. Dataset grows from 38 to 82 rows over 25 tables; `--remove` still deletes exactly the `demo-` rows.
- **A committed seed for the risk / USOAP extensible-enum vocabularies.** `ChecklistQuestion.riskLevel`, `UsoapProtocolQuestion.criticalElement` and `.areaCode`, `UsoapEvidenceExpectation.artifactCategory` and `InspectionQuestion.compliance` are `extensibleEnum` fields whose vocabularies the **tracked** entity definitions reference by hard-coded id — and AtroCore's extensible enums have no home in `metadata/` (`install-metadata.sh` syncs entityDefs, clientDefs, scopes and layouts only). So they existed *only in the database*, and a fresh install could not resolve a single risk level or USOAP Critical Element / area: `/checklist` renders `riskLevelName`/`criticalElementName`/`areaCodeName` through these enums, and `POST /api/usoap/ce-evidence-report` groups by them. `sql/seed-usoap-vocabularies.sql` + `scripts/seed-usoap-vocabularies.sh` (`make db-seed-vocabularies YES=1`) create the 5 enums and their 42 option bindings with the canonical ids, so no existing record is orphaned. Additive (`INSERT ... ON CONFLICT DO NOTHING`) and deliberately **not** removed by `seed-demo-dataset.sh --remove`. Verified by deleting all five enums inside a transaction and re-running the seed — 0 → 5 enums / 42 bindings, then rolled back with the live data untouched. `scripts/validate-seeds.py` (the `validate:seed` CI job) cross-checks the seed against the enum ids the entity definitions reference, which is how the two enums I had missed (`usoapArtifactCategory`, `compliance`) were caught.
- **`scripts/validate-seeds.py` replaces `scripts/validate-demo-seed.py`** and now covers both seed files: the demo dataset's additive-only invariants plus the vocabulary id contract.

- `metadata/` as the version-controlled source of truth for AtroCore entity metadata, with `scripts/install-metadata.sh` to install it into the gitignored `web-data/` runtime tree.
- `ActivityType` reference entity (oversight activity type: `A` Auditoría, `I` Inspección, `M` Monitoreo, `D` Revisión documental, `S` Análisis de suceso).
- `sql/seed-nomenclatura-catalog.sql` plus `scripts/seed-nomenclatura.sh` to seed the `Specialty` and `ActivityType` reference catalogs idempotently.
- `make metadata-install` and `make db-seed-nomenclatura` targets.
- **A committed synthetic demo dataset, so a fresh clone is no longer empty.** Every operational record (locations, providers, inspectors, site visits, inspections) existed only inside the binary `atrocore.dump`/`db-dumps/*.dump` files, which are gitignored and were purged from history in the P0 secret cleanup — so `git clone` + `docker compose up` produced an app with nothing to click. `sql/seed-demo-dataset.sql` + `scripts/seed-demo-dataset.sh` add one fictional airport (ICAO `ZZZZ`, ICAO's own "unknown aerodrome" placeholder, so generated codes are obviously synthetic), two service providers, three inspectors, their services and specialties, a site visit three weeks ahead of the day you seed, two inspections and the interview schedules the plan generator requires. Everything is invented (`.invalid` e-mail addresses, `Demo …` names), contains no credentials, and is **additive**: it only ever writes rows whose `id` starts with `demo-`, so it is safe against a database that already holds real records. `--remove` deletes exactly those rows. `make db-seed-demo YES=1` / `make db-seed-demo-remove YES=1`. The visit is seeded as `Planned` because `/siteVisits` hides visits that are still `Created`. Verified live: 38 rows created, 0 left after `--remove`, 38 after re-seeding, and `/siteVisits`, `/providers?siteVisit=`, `/location` and `/inspectors?specialty=` all return the demo records while the existing smoke harness stays 15/15.
- **`demo_seed_check` replaced by `validate:seed`, which actually runs.** The old job skipped itself whenever `atrocore.dump` was absent — and since dumps are gitignored, that was every run — then asserted only that "some public tables exist", which was already true against an empty database. It cannot be fixed by removing the skip: the `atro-web` image this pipeline builds starts Apache with a DocumentRoot that does not exist (the AtroCore application is never installed), so no schema is ever created and there is nothing to seed. The job is therefore replaced by `scripts/validate-demo-seed.py`, which runs in a `python:3.12-alpine` container with no Docker at all and enforces the invariants a database would otherwise only catch late: additive-only (every `DELETE` scoped to `demo-` rows), no `TRUNCATE`, every row id namespaced, the row count matching its documentation (38), and `--remove` covering every table the seed writes. Both new failure modes are verified to trip. **Open CI gap, reported rather than papered over:** the pipeline never brings up a working AtroCore, so nothing in CI exercises the metadata install or the schema sync end to end.

### Fixed

- **A clean clone could not start AtroCore at all: the application is now bootstrapped into `web-data/`.** `docker-compose.yaml` bind-mounts `./web-data:/var/www/`, and a bind mount does not inherit the image's contents — so the AtroCore app that `prepare-pim.sh` installs during the image build was hidden behind an empty host directory. On a fresh checkout `atro-web` therefore started with a DocumentRoot that did not exist, `http://localhost` served nothing, and `install-metadata.sh` aborted with *"Start the stack first (docker compose up -d --build) so AtroCore creates web-data/"* — advice the stack cannot satisfy, because it is the bind mount that prevents it. It was a named volume (`web-data:/var/www/`, which Docker *does* populate from the image) until commit `25affed` replaced it. New `scripts/bootstrap-web-data.sh` copies the image's `/var/www` into `./web-data/` once, idempotently (`--force` to re-copy); `install-metadata.sh` calls it automatically when `web-data/<domain>/` is missing, the `Makefile` exposes `make bootstrap`, and §5.1/§7.2 of the runbook document it. Verified: mounting an empty directory at `/var/www` hides the app while the unmounted image contains it, the copy step produces a complete tree (`localhost/public/index.php`, `localhost/data`) with the image's `www-data` ownership, and the script's idempotent branch is a no-op on the existing tree.
- **`install-metadata.sh` failed on Docker Desktop/Colima-style hosts when it had to write `config.php` through a container.** The script stages a temp copy of `config.php` (owned by `www-data`, so the host user cannot write it in place) and used `mktemp`, which lands in `/tmp` — a path that is not shared with the Docker daemon on those setups. Bind-mounting it gave the container an empty *directory* at `/tmp/config.php`, so `cp` reported `can't stat 'web-data/<domain>/data/config.php/config.php': Not a directory` and the install exited non-zero *after* copying the metadata. The temp copy now lives in the repository root (writable by the host user, and already mounted into the container as `/repo`), so it needs no extra bind mount at all; `.config.php.*` is gitignored against a crash leaving it behind.
- Skip ACL restoration during `pg_restore` to avoid missing-role grant failures. (`ad0513f`)
- Skip object ownership restoration during `pg_restore` to avoid missing-role ownership errors. (`db18d3f`)
- Install `bash` in the GitLab CI Alpine image to prevent shell-related job failures. (`380ab53`)
- Wait for PostgreSQL readiness in GitLab CI jobs before running checks. (`4580a6f`)
- Move GitLab CI variables to top-level scope for consistent job behavior. (`62f78f6`)
