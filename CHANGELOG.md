## [2026-09-18]

### Fixed

- **`demo-quickstart.sh`'s verify step no longer hides which check actually failed.** The smoke harness and the error-envelope audit each print one `ok`/`FAIL`/`SKIP` line per check plus a summary — piping straight through `tail -1` kept only the summary, even on failure, so a CI log showing "14 passed, 1 failed" gave no way to tell which of the 15 checks broke. Found diagnosing a `demo:verify` failure that turned out to be a pre-existing, unrelated `/findings/open` search-index-lag flake (already documented in the runbook) — confirming that took reproducing the run locally, which shouldn't have been necessary. Both calls now print their full output on failure (and still just the summary on success).

### Added

- **`THIRD_PARTY_LICENSES.md`, with a major finding: AtroCore's core packages are GPL-3.0-only.** `atrocore/core`, `atrocore/atrocore-legacy`, `atrocore/export`, `atrocore/import`, `atrocore/export-http` and `atrocore/import-http` are all GPL-3.0-only (confirmed by reading each package's bundled `LICENSE.txt` — `composer.json`'s `license` field is absent on most of them, so that file was the only reliable source; only `atrocore/slim` is MIT). These packages are compiled into the built `atro-web` image, not merely referenced the way `compliance_cmis`'s Alfresco containers are, which makes this a materially bigger open item for legal review than the already-flagged Alfresco LGPL question — GPL-3.0 is strong copyleft on the actual application core, not weak copyleft on referenced infrastructure. Specific questions for counsel are recorded in the new file.

### Fixed

- **AtroCore's GPL-3.0 source is no longer compiled into the `atro-web` image.** The install (`.docker/php/scripts/prepare-pim.sh`: clone AtroCore's skeleton, run its Composer installer, which pulls the six GPL-3.0 packages above) used to run inside `.docker/php/Dockerfile`'s `RUN` step, at `docker build` time — meaning any pre-built copy of the image carried GPL-3.0 source, unambiguous "distribution" under GPL-3.0 §6 the moment such an image was ever published. It now runs at container bootstrap instead: `scripts/bootstrap-web-data.sh` (already the script that gets AtroCore into the bind-mounted `./web-data/` on a clean clone, previously by copying a pre-baked copy out of the image) now runs `prepare-pim.sh` itself, unchanged, inside a throwaway container built from the (now install-free) image, writing the freshly-installed application straight into `./web-data/`. The Dockerfile's `RUN` step, and the nine build args (`SKELETON_VARIANT`, `PRODUCTION_DOMAIN`, DB credentials, etc.) it used to take, are gone — those values are read from `.env` by the bootstrap script instead, the same way it already read `PRODUCTION_DOMAIN`. Net effect: the `atro-web` image now contains only the generic PHP+Apache+extensions base and the (unmodified) install scripts — verified directly against the built image's filesystem, no `vendor/atrocore/*` anywhere in it — closing `THIRD_PARTY_LICENSES.md`'s open question about whether to ever publish a pre-built image (there is no longer anything GPL-flavored in it to publish). Tradeoff: first-run setup now depends on live network access to `packagist.atrocore.com`/GitHub at bootstrap time rather than at image-build time, and loses the build-time layer cache — `prepare-pim.sh` already carries scars from exactly this class of fragility (the pinned-Composer-download, IPv4-resolution workaround), worth keeping in mind if CI (`demo:verify`) sees new transient failures at this step. Verified end to end: the rewritten install produces a working AtroCore instance with all seven `vendor/atrocore/*` packages present, `scripts/` itself does not leak into `web-data/`, and re-running the bootstrap against an already-installed instance still no-ops.

Wired into `demo-quickstart.sh` between the USOAP/risk vocabularies and the nomenclatura catalog, and into `make db-seed-icao`. Additive (`INSERT ... ON CONFLICT DO NOTHING`) and, like the vocabularies seed, deliberately not removed by `seed-demo-dataset.sh --remove`. - **The gateway `API_KEY` now ships enabled by default across the platform, and the quickstart warns loudly about it.** `compliance_flow`'s `.env.example`, `compliance_web`'s and `compliance_import`'s `.env.docker.example` now set a shared public placeholder value (`API_KEY`/`NODE_RED_API_KEY`/`IMPORT_API_KEY`) instead of shipping empty — a cloned/demo stack is no longer an open gateway by default, though the placeholder itself must still be rotated before any real deployment (documented in the runbook's expanded §10). `demo-quickstart.sh` prints a loud "DEMO CREDENTIALS — DO NOT DEPLOY PUBLICLY" banner at the end of the run listing exactly what's still demo-only. Turning the key on exposed a real bug in `compliance_import`'s auth middleware — it protected `/health` too, which would have made the quickstart's own readiness probe and any compose healthcheck fail with `401` — now fixed (see that repo's CHANGELOG). `demo-quickstart.sh`'s existing service probes (Alfresco/Node-RED/import/web/AtroCore) are unaffected: `API_KEY` is exported from `compliance_flow/.env` early in the script, so `smoke-flows.mjs`/`audit-error-envelope.mjs` pick it up automatically without any script changes. **Found running an actual `demo:verify`-equivalent CI pipeline against this change (not just local testing): the quickstart's own three `compliance_import` calls (`inspection-import` ×2, `followup-import`) never sent `X-API-Key`, so a correctly-hardened stack broke its own demo at step 2 with `401 Invalid or missing API key`.** `IMPORT_API_KEY` is now read once from `compliance_import/.env` and attached to all three calls when set; empty (dev-mode, auth off) is unaffected. The next full run then failed at step 7 (`/inspectionPlan`) with the same class of gap on the `compliance_flow` side: the plain `curl` calls in `retry_json()` (plan + report generation) and the `/findings/open` check never sent `X-API-Key` either — the latter failed silently, printing `ok open demo findings: undefined` instead of catching the `401`, because it only checked that the response parsed as JSON, not that it was actually the expected list. Both fixed: a `FLOW_AUTH_HEADER` array (built from `API_KEY`, already sourced from `compliance_flow/.env`) is now attached to every plain `curl` call this script makes to Node-RED, and `/findings/open`'s result is now asserted to be numeric or the script dies with the actual response instead of silently reporting `undefined`. This is exactly the kind of gap unit tests and isolated live checks don't catch — only running the quickstart itself, end to end, with the key actually on, surfaced it.
- **The quickstart now checks Alfresco/Solr/ActiveMQ/transform-core-aio container health directly, not just Alfresco's own readiness endpoint.** `FOOTPRINT_AUDIT.md` (2026-09-15) found a dead ActiveMQ produces no error at all — specific operations (replanning an existing document) simply hang forever — the worst failure mode for an unattended install, since Alfresco's `/probes/-ready-` stays green regardless. Step 0 now also greps `docker compose ps` in `compliance_cmis` for `unhealthy` on those four services and fails fast with a clear message before anything downstream can hang silently instead.
- **Alfresco's memory limit raised `1900m` → `2560m` in `compliance_cmis/docker-compose.yml`.** `FOOTPRINT_AUDIT.md` measured it idling at 1.759 GiB of a 1.855 GiB cap — 95-97% utilized before any real load — which risks GC-thrashing or an OOM kill under actual demo activity (imports, PDF generation). ### Fixed

- **The demo quickstart and its CI guard were finished off by the first runs that actually reached the end of the demo.** Five defects, each invisible until the whole stack was booted from an empty checkout: the smoke harness and the error-envelope audit defaulted to `http://localhost:1880` — the machine they run *on*, which on a runner is the job container, not the stack — so all fifteen checks failed on connection with nothing pointing at the URL (they already read `BASE`; the quickstart now sets it from `DEMO_HOST`); the follow-up step answered `processed: 0` because the canonical import resolves the finding through the **search index** and the finding was created seconds earlier, so the step retries (the call is an upsert) and prints the full summary plus the repository log when it gives up; plan and report generation answered `HTTP 500` on a cold runner until LibreOffice has started inside the transform service, so the retry window is now ten attempts fifteen seconds apart, with the log on failure; `node` was missing from the job (the quickstart parses every response with it — runbook §1.1 lists it) and the script now checks `docker`, `curl`, `python3`, `node` and `git` up front; and the guard's exported `ATROCORE_BASE_URL`/`ALFRESCO_URL` leaked host-only addresses into the containers through compose interpolation (`Failed to resolve 'docker'`), so the host-facing values are now scoped to the two commands that need them — containers keep their in-network addresses from their own `.env` files. Also removed two scratch files (`.ci-job`, `.trace.txt`) that `git add -A` had swept into a merged commit, and ignored both names. **Result: `demo:verify` is green end to end from an empty checkout in 7m24s** — five services up, install, schema, 90-row seed, identities, site content, both imports, the follow-up to `Pending Closure Approval`, smoke 15/15, envelope audit 5/5, and the plan, report, provider history and USOAP CE-5 evidence.

### Added

### Added

- **A CI guard that runs the whole-stack demo (`demo:verify`).** `validate:fresh-install` covers AtroCore and the three seeds; everything after that — the demo identities, the payload imports, the canonical documents, the closure walkthrough and the oversight artifacts — needs all six repositories side by side, which a single-repo checkout does not have, so it was only ever verified by hand. New `scripts/demo-verify-ci.sh` assembles that layout (it clones the five siblings over HTTPS at `develop` — all six projects are public — and merges the minimum settings each service needs into their `.env` files without touching anything else), creates the three external networks, validates every compose file, brings the stack up in the runbook's order, waits for each service and then runs `scripts/demo-quickstart.sh --yes`. A `--prepare-only` mode does the clone/env/network/compose-config half in seconds, which is how the wiring was verified locally, and `--teardown` brings every project down and removes the networks, so a failed run does not leave five stacks on the runner. The job is **manual/scheduled, not a merge-request gate**: it builds five projects and boots Alfresco, Solr, ActiveMQ, the transform service, Node-RED and two Node services, so it takes on the order of twenty minutes and needs a runner with memory to match — a schedule is the only way this stays checked without someone remembering to press a button, and `SIBLING_REF` decides which sibling branch it tests (default `develop`, so it answers "does the demo work on today's integration branches?").

### Changed

- **The demo quickstart now derives every payload date from the seeded site visit, instead of importing the dates frozen into the tracked ZIPs.** The seed computes the site visit's window relative to the day it runs (`CURRENT_DATE + 21`/`+ 22`, §1 of `sql/seed-demo-dataset.sql`), while a ZIP committed to `compliance_import` freezes its dates the day it is written — so the demo drifted within a day of the payloads being built, and the drift was not cosmetic: the canonical import copies `checklist.startDate`/`endDate` onto the Alfresco inspection folder, which is the only place an inspection's window lives (`inspection` in AtroCore has no date columns), so a stale payload dated the inspection into the wrong week and its checklist items fell out of the year-filtered provider-history report. The stamping is a no-op when re-run on the same window, so the quickstart stays idempotent. Verified live: the seeded window `2026-10-07 → 2026-10-08` is what both `AV-ZZZZ-A-0001` and `AV-ZZZZ-I-0001` now carry (the ATS payload's template window was `2026-10-06 → 2026-10-07`), with its findings re-dated to `2026-10-08` and the follow-up to `2026-10-21`.

### Fixed

- **A fresh clone's AtroCore was scaffolded but never *installed*, so every API call answered `500`.** `docker compose up -d --build` builds the application files; it does not run AtroCore's installation. A fresh instance therefore had `'isInstalled' => false` in `data/config.php` and an empty `user` table, so `/api/v1/App/user` answered `500` with an empty body, `compliance_flow`'s `/specialties` answered `400`, and `compliance_web` login could not work — the platform was unusable however green the seeds were. New `scripts/install-atrocore.sh` drives AtroCore's own web wizard (`POST /api/v1/Installer/setLanguage`, then `/createAdmin`) non-interactively, with the credentials the platform already uses (`ATROCORE_USERNAME`/`ATROCORE_PASSWORD` in `compliance_flow/.env`), so the super admin is the account Node-RED authenticates as. Two non-obvious things it encodes: the installer API path is `/api/v1/Installer/<action>` — **not** the usual `/api/v1/<Controller>/action/<action>`, and `Application::runInstallerApi()` swallows every `Throwable` into a bodiless `500`, so a wrong path is indistinguishable from a real failure; and `createAdmin` calls `Installer::prepareDataBase()`, which **drops every table** and rebuilds from the application's metadata, so the script refuses to run when the app already reports itself installed and requires `--yes`. Verified on a genuinely fresh instance: `isInstalled => true`, `user` row `1 admin` with `is_admin`, `/api/v1/App/user` → `401`.
- **Console commands now run as `www-data`, and the quickstart can finally run on a raw clone.** Three ordering/permission defects, all found by running the documented path against a freshly recreated database. (i) `docker compose exec` defaults to **root**, so `clear cache` / `sql diff --run` left root-owned files in `data/cache`; the web process then failed its next cache write and answered `500` on every API route, with nothing in the Apache log (the message is `file_put_contents(data/cache/listeners.json): Permission denied` in `data/logs/`). Every console invocation in the scripts, the README and the runbook now uses `-u www-data`. (ii) The preflight probed AtroCore *before* step 0b bootstrapped it — on a clean clone `web-data/` is empty, so Apache has no DocumentRoot and answers `404`, and Node-RED's `/specialties` answers `400` because it proxies to AtroCore. The independent services are probed first and AtroCore, its schema and Node-RED are checked after step 0b. (iii) Step 0b installed the metadata but never installed the application, so the schema and the admin user were still missing; it now runs `install-atrocore.sh` between the bootstrap and the metadata install.
- **The image build has been broken since 2026-08-07, and the application version was never pinned.** Both skeleton repositories moved that day ("Update atrocore/core version and rename installer files" — `skeleton-atrocore@af44164`, `skeleton-pim-no-demo@b350ca3`), renaming `composer.phar` to `atrocore-installer.phar`. `prepare-pim.sh` still ran `php composer.phar self-update && php composer.phar update`, so a clean build failed; and because `\Atro\Composer\PostUpdate::getRootPath()` locates the project root by walking up until it finds a directory containing `composer.phar`, driving the new installer also failed with `Failed! Can't find root directory.` The build now pins each skeleton revision per variant, downloads Composer itself (2.8.12, sha256-verified — it satisfies that marker and remains a fallback tool), and lets the AtroCore installer drive the install. The installer is required, not merely preferred: the public package listing (`packagist.atrocore.com/packages.json`, 53 packages) carries `atrocore/core`, `export` and `import` but omits `atrocore/atrocore-legacy` and `atrocore/slim`, which `core` requires — plain `composer update` resolves neither. `COMPOSER_IPRESOLVE=4` works around the builder resolving `repo.packagist.org` to IPv6 and being unable to route it, and `first_update.log` is removed so `PostUpdate::uploadDemoData()` does not pull AtroCore's own demo dataset over this project's.
- **The application version is now pinned — which is what made the vocabulary seed fail on a fresh install.** The skeleton's `composer.json` floats (`atrocore/core >=2.3.12`, `export`/`import` `*`) and the build ran `update`, so the installed app, and therefore the database schema, changed with wall-clock time: the running instance was `atrocore-legacy 1.1.11` / core `2.0.23`, while a fresh build pulled `1.2.12` / core `>=2.2.30`. `ExtensibleEnum.json` lost its `multilingual` field somewhere between core 2.1.6 and that line, so `seed-usoap-vocabularies.sh` died with `column "multilingual" of relation "extensible_enum" does not exist` on a clean install while working on the long-lived instance. New `.docker/php/scripts/composer.pinned.json` pins `atrocore/core 2.1.6`, `atrocore/export 1.10.1`, `export-http 1.8.0`, `import 1.10.2`, `import-http 1.6.1` — the top of the range this repository itself declared (`>=2.0.23 <=2.1.6`) — against the public repository, with no account id and with Composer's security-advisory blocking left **on** (pinning the exact 1.1.11 set would have required disabling it, because `phpspreadsheet 1.16.0` carries published advisories; 2.1.6 resolves `1.30.6`). Verified on an isolated fresh instance: the image builds, the app serves, `extensible_enum` has `multilingual`, and `seed-usoap-vocabularies.sh` + `seed-nomenclatura.sh` both succeed. The demo dataset still needs the operational model, which remains P2.6 in `TECHNICAL_DEBT_ANALYSIS.md`.
- **A clean clone could not start AtroCore at all: the application is now bootstrapped into `web-data/`.** `docker-compose.yaml` bind-mounts `./web-data:/var/www/`, and a bind mount does not inherit the image's contents — so the AtroCore app that `prepare-pim.sh` installs during the image build was hidden behind an empty host directory. On a fresh checkout `atro-web` therefore started with a DocumentRoot that did not exist, `http://localhost` served nothing, and `install-metadata.sh` aborted with *"Start the stack first (docker compose up -d --build) so AtroCore creates web-data/"* — advice the stack cannot satisfy, because it is the bind mount that prevents it. It was a named volume (`web-data:/var/www/`, which Docker *does* populate from the image) until commit `25affed` replaced it. New `scripts/bootstrap-web-data.sh` copies the image's `/var/www` into `./web-data/` once, idempotently (`--force` to re-copy); `install-metadata.sh` calls it automatically when `web-data/<domain>/` is missing, the `Makefile` exposes `make bootstrap`, and §5.1/§7.2 of the runbook document it. Verified: mounting an empty directory at `/var/www` hides the app while the unmounted image contains it, the copy step produces a complete tree (`localhost/public/index.php`, `localhost/data`) with the image's `www-data` ownership, and the script's idempotent branch is a no-op on the existing tree.
- **`install-metadata.sh` failed on Docker Desktop/Colima-style hosts when it had to write `config.php` through a container.** The script stages a temp copy of `config.php` (owned by `www-data`, so the host user cannot write it in place) and used `mktemp`, which lands in `/tmp` — a path that is not shared with the Docker daemon on those setups. Bind-mounting it gave the container an empty *directory* at `/tmp/config.php`, so `cp` reported `can't stat 'web-data/<domain>/data/config.php/config.php': Not a directory` and the install exited non-zero *after* copying the metadata. The temp copy now lives in the repository root (writable by the host user, and already mounted into the container as `/repo`), so it needs no extra bind mount at all; `.config.php.*` is gitignored against a crash leaving it behind.
