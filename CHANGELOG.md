# Changelog

All notable changes to this project are documented in this file.

The format is inspired by Keep a Changelog and releases are dated — see CONTRIBUTING.md, "Versioning and releases".

## [Unreleased]

### Added

- **A default layout profile is now installed with the metadata, and the tracked layouts are materialised into it.** AtroCore loads layout *content* from the `layout` database table (per profile) or from the core/module resource trees — **never from `data/layouts/`**, where `install-metadata.sh` copies `metadata/layouts/`. So the tracked layouts were inert, and the stock profile's menu (Product/File/Attribute/Classification/ImportFeed/ExportFeed) contained none of this platform's entities, making every one of them unreachable in the admin UI. New `scripts/install-layouts.sh` (also `make install-layouts YES=1`):
  - applies `sql/seed-layout-profile.sql`, which gives the existing `default` profile a platform menu (Vigilancia, Entidades reguladas, Recursos, Cumplimiento USOAP, Catálogos, Intercambio de datos, Sistema) — 26 platform entities in 7 groups, i.e. all 32 minus the six deliberately omitted. The `InspectedProvider`/`InspectedService`/`InspectedSpecialty` records the planning flow creates **are** included: they are neither Alfresco-stored nor unused. Deliberately absent: `Finding`/`CorrectiveAction*` (Alfresco-stored), `ActingInspector` (disconnected) and `Tag` (not enabled in the UI). Idempotent, and it does not force `is_default` on an existing profile.
  - sends each `metadata/layouts/<Entity>/{list,detail,kanban,relationships}.json` to AtroCore via `PUT /api/v1/<Entity>/layout/<view>?layoutProfileId=default`, so AtroCore's own `Layout::saveContent` writes the child tables. Related-scope layouts (`detailIn*/listIn*`) are sent with a `relatedScope` argument; the recovered `listDashlet` files were removed (see below).
  Wired into `demo-quickstart.sh` and both fresh-install CI jobs, which assert the profile's 7 groups and 123 materialised layouts.
- **`FindingSeverity` is now seeded (A/B/C).** `compliance_web`'s `server/findings/severityDeadlines.cjs` queries it live and throws when the severity has no record, so on a fresh install the review action could not set a severity at all. The day counts are the authority's own, taken from the reference DR deployment: A = 7 days to solution / 3 to submit, B = 30 / 15, C = 90 / 30 (the solution windows also match the field app's `app.config.json`). Upsert, not replace — an admin's tuned values survive a re-run.
- **The dead `listDashlet` layouts were removed (29 files).** They were part of the recovered metadata, but `listDashlet` is referenced nowhere in this AtroCore version and `Layout::saveContent` has no case for it, so they could never be materialised — writing one would have stored an empty custom layout and hidden AtroCore's own default. `scripts/install-layouts.sh` no longer needs its skip branch.
- **The Spanish (`es_DO`) labels for `compliance`, `findingClass` and `inspectorRoles` are now installed: `scripts/enable-spanish-labels.sh` + `sql/seed-vocabulary-translations.sql`.** AtroCore only creates a multilingual field's sibling columns (here `name_es_do`) once a second language is configured as *additional*; a fresh install has only `en_US` as `main`, which is why the debt analysis recorded those vocabularies showing English labels in a Spanish-language product. The script adds `es_DO` to the `Language` reference data, runs `clear cache` + `sql diff --run` so the columns exist, then seeds the DR instance's labels (Cumple / No Cumple / No Aplica; Categoría A/B; Inspector Principal / Secundario / Miembro de Equipo). Idempotent, and the English `name` is kept alongside. Wired into `demo-quickstart.sh` and both fresh-install CI jobs, which assert 8 labelled options. **Verified live:** `GET /api/v1/ExtensibleEnumOption` returns `nameEsDo: "Cumple"` for the `Compliant` option.
- **A starter authority dataset for adopters: `sql/seed-starter-dataset.sql` + `scripts/seed-starter-dataset.sh` (`make db-seed-starter YES=1`).** Standing up a deployment previously meant hand-entering `Location`, `ServiceProvider`, `Person`, `Inspector`, `ServiceArea`, `AssignmentGroup`, `Reglamento` and `Normativa` before anything could be planned, with no worked example of how they connect. This ships a minimal, coherent set of clearly-marked placeholders (13 rows across 12 tables, e.g. provider → contact → inspector → location service → cadence, and regulation → article) so an adopter can see the shape and edit it into real data. Namespaced `starter-`, additive and `ON CONFLICT DO NOTHING`, so re-running never overwrites an edit; `--remove --yes` deletes exactly those rows. It is **not** run by the demo quickstart — it is the counterpart to the synthetic `demo-` dataset, not a companion; `validate-seeds.py` now checks its invariants (namespacing, no TRUNCATE/DELETE, `--remove` coverage) alongside the demo seed's. `InspectionCadence` was initially dropped from it, because its `inspectedProvider` was a required link to `InspectedProvider`, an operational per-site-visit record, which made the seeded cadence a dangling reference; that turned out to be a modelling defect rather than a seeding one and is fixed under "Changed" below, so the starter cadence is back. `--remove` also clears the join rows an import created by their starter parent, so a remove-then-reseed no longer trips the `(parent, child)` unique index.
- **Authority data packs: the same starter records as editable CSV, loaded through AtroCore's own import module (`data-packs/`, `scripts/import-data-pack.py`, `make import-data-packs [PACK=...]`).** The seed above requires `psql`; the person who enters a civil aviation authority's locations, providers, contacts, inspectors and regulations usually does not have it. Each pack is a CSV template (`Location.csv`, `ServiceProvider.csv`, `Person.csv`, `Inspector.csv`, `Reglamento.csv`, `Normativa.csv`, `LocationService.csv`, …) plus its column mapping in `data-packs/packs.json`, and a stdlib-only runner that does what would otherwise be clicked through in the import UI: ensure the `ImportFeed` (keyed on `code`, `fileDataAction=create_update`), ensure one `ImportConfiguratorItem` per mapped column (pruning columns the pack no longer maps, which would otherwise keep writing their default), convert the CSV rows to JSON, run `POST /ImportFeed/action/easyCatalog` — no file upload — and poll the resulting `ImportJob`, printing one line per failed row and exiting non-zero. Rows are matched on `ID` and upserted, so editing a value and re-running updates it and re-importing unchanged data writes nothing. Ten packs, eleven rows, imported in dependency order by `--all`. `scripts/validate-data-packs.py` (container-free, wired into both `validate:seed` jobs) checks the mapping against `metadata/entityDefs/`, the CSV headers, the `starter-` namespacing and that each pack's ids are exactly the ids the SQL seed writes for that entity; the `fresh-install` CI jobs now apply the starter seed and then import every pack, so a pack whose links or required fields do not fit the metadata fails there. `data-packs/README.md` documents the mapping and how to add a column or a pack.

### Changed

- **Data-pack relationship columns resolve by human key where the related entity has one, and `importBy` is now validated against that entity's real fields.** `Normativa.csv` names its regulation by `codigo` (`RegulationCode`, `RAD-XXXX`) instead of `starter-reglamento-01`, and `LocationService.csv` names its location by `icaoCode` (`LocationICAO`, `XXXX`) instead of `starter-loc-01`, so an adopter filling in a spreadsheet does not have to look opaque ids up. `validate-data-packs.py` previously checked `importBy` against a fixed `{id, code, name}` allowlist, which both rejected legitimate keys like `codigo` and accepted names that do not exist on the target; it now resolves the column's link to the related entity and requires the named attribute to exist there, be storable, and have a type the import module can match by (mirroring `Import\FieldConverters\Link::ALLOWED_TYPES`).
- **`scripts/import-data-pack.sh` is the entry point, so the command matches every other script in `scripts/`.** It execs the Python implementation, which stays where the JSON-shaped mapping work belongs. `make import-data-packs`, both CI jobs and the READMEs now call the wrapper rather than the `.py` directly.
- **`InspectionCadence` now hangs off `LocationService` instead of the per-visit `InspectedProvider`** (`sql/migrations/0002_repoint_inspection_cadence_to_location_service.sql`). A cadence records how often a service is due an inspection, and `compliance_web`'s daily scheduling job reads it to *create* SiteVisits — but `inspectedProvider` is a junction row that only exists once a SiteVisit has been planned, so the entity that triggers the first visit could not be created until a visit already existed. The provider picker was empty on a fresh install, and neither onboarding path could seed a cadence. `LocationService` is the authority-side registry of which provider offers which specialties at which location, which is the grain a cadence actually has; anchoring there also makes impossible combinations unrepresentable, where three independent `serviceProvider`/`location`/`specialty` links could express a radar-specialty cadence at a location with no radar. Concretely: `inspectedProvider` → `locationService` (required), the now-derivable `location` link dropped, the reciprocal moved from `InspectedProvider`/`Location` to `LocationService`, `LocationService.location` and `.serviceProvider` tightened to required (the cadence depends on the first), and a new `uniqueIndexes` entry on (`deleted`, `location_service_id`, `specialty_id`, `activity_type_id`) so one service cannot accumulate duplicate conflicting cadences. The migration backfills `location_service_id` from each cadence's old `inspected_provider` (provider) and its SiteVisit (location); the cadence's specialty is a **hard** filter on that match, not a tiebreak, because one provider routinely has several services at one location and a soft preference would silently file a NAV cadence against an ATS service — an unresolvable live row aborts the migration with instructions instead. Duplicates abort too, since `sql diff --run` creates the unique index immediately afterwards. The starter seed and a new `inspection-cadence` data pack both ship a cadence again (with `nextDueDate` in 2027, so the scheduling job does not create a visit on a fresh install), and `LocationService.csv` gains a `SpecialtyCodes` column because a cadence's specialty is only meaningful if the service covers it.
- **`scripts/migrate-db.sh` is now run by both fresh-install CI jobs, and migration `0001` is guarded.** Nothing invoked the migration runner, so neither migration had ever been executed in CI. Wiring it in (before `install-metadata.sh`, because `sql diff` drops columns a migration may still need to read) immediately showed that `0001` fails wherever `protocol_question` no longer exists — a fresh install, whose schema is built from entityDefs that already say `ChecklistQuestion`, or any instance renamed before the runner existed. It now skips with a notice instead, like `0002`. Both migrations are written to be idempotent, which also contains a pre-existing conflict worth knowing about: AtroCore diffs the whole database against `entityDefs` with no asset filter (`Schema.php::getDiffQueries`), so `sql diff --run` proposes `DROP TABLE schema_migrations` and wipes the runner's ledger. Re-running the runner is therefore a no-op rather than a second application; `migrate-db.sh` now says so on exit. Also adds `make db-migrate` / `make db-migrate-status`, which did not exist.

- **`metadata/layouts/` regenerated from the reference Dominican-Republic instance's layout tables.** The tracked layouts were near-empty stubs (list views with a single `name` column, detail views with one section and two fields) — recovered from an instance whose layout customisations lived in its database, not its metadata files. A previous AtroCore deployment configured for the DR (`compliance` database, layout profile `a01jwnr4h7ye5hbwz1jv0zwmzye`) holds the real ones: 100 custom layouts. 66 of our layout files are now derived from it — list views go from 1 column to 2–7 (`Inspector`: `name, organizationID, specialty`; `ChecklistQuestion`: 7; `Finding`: 5), detail views from 1 section/2 fields to 2–10 (`Person`: 8, `Inspection`: 8, `SiteVisit`: 7), and 19 relationship panels are added. The derivation, in outline:
  - only **non-deleted** rows are read (soft-deleted duplicates in the DR database accounted for e.g. five identical `UsoapProtocolQuestion` detail sections, which collapse to the one active section);
  - entity renames applied: `ProtocolQuestion`→`ChecklistQuestion`, `RegulatoryDocument`→`DocumentoOACI`;
  - field renames applied where the tracked model differs: `protocolQuestion`→`checklistQuestion`, `protocolQuestions`→`checklistQuestions`, `siteVisits`→`siteVisit` (InspectedProvider), `inspectedProvider`→`inspectedProviders` (SiteVisit), `inspectedService`→`inspectedSpecialty`, `InspectorSpecialty__id`→`specialty`, `parent`→`parents` (ServiceProvider, Tag), `inspectionType`→`activityType`;
  - references with no counterpart in the tracked `entityDefs` are dropped rather than carried — mostly the links deliberately removed in the earlier cleanup (`Finding.correctiveActions`, `InspectedService.findings`, …), plus `Specialty.id` and layouts for entities this repo does not track (`ContactInfo`, `LocationProvider`);
  - an existing layout was kept when it had more valid fields than the derived one, and every file was then re-checked so no layout references a field its `entityDef` does not define (this removed a pre-existing bad `parent` from `ServiceProvider/detail` and `Tag/detail`);
  - an empty layout is never written — that would store a custom layout with no fields and hide AtroCore's own default.
  The DR layouts scoped to a related entity are adopted too: 9 become `detailIn*/listIn*` files (`Inspector` detail inside `Specialty.inspectors`; `ChecklistQuestion` under `Specialty` and `InspectionQuestion`; `AcapiteOACI` under `DocumentoOACI`; `DocumentoOACI` under `AcapiteOACI`; `InspectionQuestion` under `ChecklistQuestion`), and `scripts/install-layouts.sh` now sends the `relatedScope` argument for them (recovering the link's real case from the file name, which AtroCore writes with `ucfirst`). Three are dropped because their links do not exist in the tracked model: `AcapiteOACI.documento` (our link is `documentoOACI`) and `CorrectiveActionPlan.correctiveActions` (from the removed cluster). Materialised layout count rises 95 → 114 → 123.

- **The tracked model now reflects the instance's link cleanup: the unused entity cluster is disconnected.** `ActingInspector`, `Finding`, `CorrectiveAction`, `CorrectiveActionPlan` and `CorrectiveActionFollowUp` had their relations removed on the running instance — `Inspector.actingInspectors`, `Finding.{correctiveActions,inspectedService,inspectionQuestions}`, `CorrectiveAction.{correctiveActionFollowUps,correctiveActionPlan,findings}`, `CorrectiveActionPlan.{correctiveActions,inspectedServcies}`, `CorrectiveActionFollowUp.correctiveAction`, `InspectedService.{correctiveActionPlan,findings}` and `InspectionQuestion.findings` — and `sql diff --run` dropped the corresponding columns. The entity definitions remain (so the tables and, where relevant, the framework fields stay), but nothing links to or from them. Captured with `make metadata-export`; `make metadata-drift` is clean again. **Note:** the definitions are still `entity: true, tab: true, disabled: false`, so they remain visible in the AtroCore UI until a navigation/layout decision says otherwise. To be precise about which entities are unused: the five are `ActingInspector`, `Finding`, `CorrectiveAction`, `CorrectiveActionPlan` and `CorrectiveActionFollowUp`; `InspectedService` and `InspectionQuestion` are **used** — they only lost their links into that cluster, and both stay in the default profile's navigation.

### Fixed

- **The USOAP evidence-expectation catalog was never loaded by a default install — and could not have been.** `scripts/seed-usoap-evidence-expectations.sh` / `sql/seed-usoap-evidence-expectations.sql` (48 rows, one per Protocol Question whose ICAO guidance asks for a sample across a whole population of artifacts) existed and was documented, but nothing ran it: not the README checklist, not `demo-quickstart.sh`, not the fresh-install CI jobs. Wiring it in turned up why it had stayed out: its safety-net block re-created the `usoap_artifact_category` enum with `ON CONFLICT (id) DO NOTHING` on the option-link table, while `seed-usoap-vocabularies.sql` had since become the canonical home for that enum and creates the same relations under different `vocab-link-*` ids — so the conflict was on the `(deleted, extensible_enum_id, extensible_enum_option_id)` unique index and the whole seed aborted with `duplicate key value violates unique constraint`. The link insert now uses `ON CONFLICT DO NOTHING`, so the seed is idempotent whether or not the vocabularies seed has run, and it is now wired into the README checklist, `demo-quickstart.sh`, both `fresh-install` CI jobs (between the ICAO seed and the nomenclatura catalog — the order it needs, since it resolves every row to its parent PQ by `code`), `make db-seed-usoap-evidence YES=1` and runbook §7.2. It is ICAO-derived and CAA-independent: the ten artifact categories map to Alfresco node types in `compliance_cmis`'s `webscripts/usoap/generate-ce-evidence-report.post.js` (`POPULATION_CATEGORY_TYPES`), which is what resolves the report's "Type-2" sampled-population PQs. `validate-seeds.py` now guards all of it — 48 unique rows, every `pq_code` present in the ICAO seed, the artifact-category options identical to the vocabularies seed's, and its `DELETE` scoped to `usoap_evidence_expectation` — and both CI jobs assert 48 rows and 0 unresolved parents. Verified on a throwaway copy of the real schema: 48 rows with 0 NULL parents after the ICAO seed, unchanged on a re-run, and still safe standalone (the safety net creates the enum, the rows land with a NOTICE that they could not resolve their PQ).
- **`scripts/import-data-pack.py` reported a large import's outcome from a capped page, so it could pass a failing import.** `summarise()` fetched `ImportJobLog` with `maxSize=200` and derived both the per-type counts and the error list from that page. The collection endpoint returns rows in arbitrary order, so a large pack under-reported (importing 3,393 regulation articles printed `create=200`) and — the real defect — a row error beyond the sampled page was never seen, so `collect_pack()` returned success and `--all` exited 0 over a failing import. Counts now come from each filtered collection's `total` (one query per log type plus one for the job), and error messages are fetched with their own `type=error` filter whose total is reported even when more than a page exists. A CSV with no data rows is skipped with a message instead of submitting an empty payload that only creates a job with no log rows. Found while rehearsing the reference dataset import: a 250-row file whose 240th row was invalid reported `skip=200` and exited **0** before the change, and `create=249, error=1` with a non-zero exit after it.
- **`scripts/validate-metadata.py` no longer requires a `links` key on every entity definition.** The link cleanup removed the key entirely from five definitions, which AtroCore treats as "no links"; the validator now requires `fields` and validates `links` only when present.
- **`make metadata-drift` no longer compares the non-runtime `data/layouts` tree.** It compared `metadata/layouts/` against `web-data/<domain>/data/layouts/`, which AtroCore never reads — so it could only ever confirm that the last `install-metadata.sh` copy ran, and an administrator's layout edit (which lands in the `layout` database table) was invisible to it either way. The check now covers entityDefs/clientDefs/scopes and prints an explicit note that layouts are DB-backed and reconciled by `scripts/install-layouts.sh`.
- **`scripts/install-layouts.sh` sent the wrong auth header for the Layout route.** It used `Authorization: Bearer`, which that route rejects with HTTP 400 `None of security schemas did match` — its OpenAPI security scheme is an apiKey header named `Authorization-Token` (AtroCore's entity routes, which Node-RED uses, accept Bearer; this one does not). Fixed, and **verified live against the running instance**: `make install-layouts YES=1` materialised all 123 layouts into the `default` profile (`Inspector/layout/list` now returns `name, organizationID, specialty`, `Person/layout/detail` returns its 8 fields), with the 7-group platform menu intact.

### Documentation

- **The quickstart checklist no longer stops at a UI with no menu.** The "First 5 Minutes Checklist" jumped from "install the metadata and create the schema" straight to "open http://localhost", and lumped three *reference* seeds in with the synthetic demo dataset under "Optional". An adopter following it exactly got AtroCore's stock menu, none of the platform's entities reachable, and no import feeds — with nothing in the checklist to explain it. The checklist now has explicit steps for the reference catalogs (`seed-usoap-vocabularies`, `seed-icao-reference-data`, `seed-nomenclatura` — needed by any deployment, and required before the data packs can resolve a `SpecialtyCode`, `ActivityTypeCode` or `AnnexParagraphID`) and for `install-layouts.sh`, and says plainly that a fresh install has **no import feeds** until the pack runner has run (they are created over the API; no `ImportFeed` metadata is tracked). The Layouts section now leads with the fact that the menu is `layout_profile.navigation` and the layouts are the `layout` table — `install-metadata.sh` copying `metadata/layouts/` into `data/layouts/` is inert. Runbook §7.2's command block gets `install-layouts.sh` and the same reference-vs-demo-seed correction, and `make help`'s quickstart line (which printed a literal `@echo` because two `@echo` sat on one line) is fixed and lists the required steps.
- **README's CI section now describes the jobs that actually exist.** It still listed `blank_instance_check` (replaced by the merge-gated `validate:fresh-install`), said "three validation jobs" (there are four, `demo:verify` included), and quoted the demo dataset as "73 rows" (it is 90, which `scripts/validate-seeds.py` enforces). The note below it, which explained why the seed could not run in CI, is also superseded — `validate:fresh-install` bootstraps the application and runs all four seeds on an empty database.
- **`scripts/demo-quickstart.sh`'s header no longer calls `metadata/` a "partial overlay".** The tree is the whole operational model (32 entities with client definitions, scopes and layouts); the old wording dated from before it was recovered. The `.gitlab-ci.yml` comment above `demo:verify` says "four seeds", not three.

## [2026-09-18]

### Fixed

- **`demo-quickstart.sh`'s verify step no longer hides which check actually failed.** The smoke harness and the error-envelope audit each print one `ok`/`FAIL`/`SKIP` line per check plus a summary — piping straight through `tail -1` kept only the summary, even on failure, so a CI log showing "14 passed, 1 failed" gave no way to tell which of the 15 checks broke. Found diagnosing a `demo:verify` failure that turned out to be a pre-existing, unrelated `/findings/open` search-index-lag flake (already documented in the runbook) — confirming that took reproducing the run locally, which shouldn't have been necessary. Both calls now print their full output on failure (and still just the summary on success).

### Added

- **`THIRD_PARTY_LICENSES.md`, with a major finding: AtroCore's core packages are GPL-3.0-only.** `atrocore/core`, `atrocore/atrocore-legacy`, `atrocore/export`, `atrocore/import`, `atrocore/export-http` and `atrocore/import-http` are all GPL-3.0-only (confirmed by reading each package's bundled `LICENSE.txt` — `composer.json`'s `license` field is absent on most of them, so that file was the only reliable source; only `atrocore/slim` is MIT). These packages are compiled into the built `atro-web` image, not merely referenced the way `compliance_cmis`'s Alfresco containers are, which makes this a materially bigger open item for legal review than the already-flagged Alfresco LGPL question — GPL-3.0 is strong copyleft on the actual application core, not weak copyleft on referenced infrastructure. Specific questions for counsel are recorded in the new file.

### Fixed

- **AtroCore's GPL-3.0 source is no longer compiled into the `atro-web` image.** The install (`.docker/php/scripts/prepare-pim.sh`: clone AtroCore's skeleton, run its Composer installer, which pulls the six GPL-3.0 packages above) used to run inside `.docker/php/Dockerfile`'s `RUN` step, at `docker build` time — meaning any pre-built copy of the image carried GPL-3.0 source, unambiguous "distribution" under GPL-3.0 §6 the moment such an image was ever published. It now runs at container bootstrap instead: `scripts/bootstrap-web-data.sh` (already the script that gets AtroCore into the bind-mounted `./web-data/` on a clean clone, previously by copying a pre-baked copy out of the image) now runs `prepare-pim.sh` itself, unchanged, inside a throwaway container built from the (now install-free) image, writing the freshly-installed application straight into `./web-data/`. The Dockerfile's `RUN` step, and the nine build args (`SKELETON_VARIANT`, `PRODUCTION_DOMAIN`, DB credentials, etc.) it used to take, are gone — those values are read from `.env` by the bootstrap script instead, the same way it already read `PRODUCTION_DOMAIN`. Net effect: the `atro-web` image now contains only the generic PHP+Apache+extensions base and the (unmodified) install scripts — verified directly against the built image's filesystem, no `vendor/atrocore/*` anywhere in it — closing `THIRD_PARTY_LICENSES.md`'s open question about whether to ever publish a pre-built image (there is no longer anything GPL-flavored in it to publish). Tradeoff: first-run setup now depends on live network access to `packagist.atrocore.com`/GitHub at bootstrap time rather than at image-build time, and loses the build-time layer cache — `prepare-pim.sh` already carries scars from exactly this class of fragility (the pinned-Composer-download, IPv4-resolution workaround), worth keeping in mind if CI (`demo:verify`) sees new transient failures at this step. Verified end to end: the rewritten install produces a working AtroCore instance with all seven `vendor/atrocore/*` packages present, `scripts/` itself does not leak into `web-data/`, and re-running the bootstrap against an already-installed instance still no-ops.

### Added

- **The vanilla install now ships the real ICAO reference catalog, not just the synthetic demo's `PQ 99.x` chain.** The USOAP citation chain (`ChecklistQuestion → Normativa → AcapiteOACI → UsoapProtocolQuestion`) had no ICAO Annex documents, Annex paragraphs or Protocol Questions on a fresh install — `sql/seed-usoap-evidence-expectations.sql` already depended on `usoap_protocol_question` being populated (it resolves each row's parent PQ by `code` via a subquery) and silently resolved every row to a `NULL` parent without it. New `scripts/seed-icao-reference-data.sh` / `sql/seed-icao-reference-data.sql` load **15 Annex documents, 1,890 Annex paragraphs, 281 USOAP Protocol Questions and 439 PQ → paragraph citations**, extracted from a legacy database snapshot that predates the synthetic demo dataset and filtered to real (non-`demo-`) rows. Unlike `Normativa` — a specific country's national regulation, deliberately never seeded — this content is ICAO-standard and CAA-independent, so it belongs in every install rather than something each adopting authority re-enters by hand. Wired into `demo-quickstart.sh` between the USOAP/risk vocabularies and the nomenclatura catalog, and into `make db-seed-icao`. Additive (`INSERT ... ON CONFLICT DO NOTHING`) and, like the vocabularies seed, deliberately not removed by `seed-demo-dataset.sh --remove`. Verified live end to end against a fresh schema: all four inserts land exactly (15/1,890/281/439), a second run inserts 0 rows, every `critical_element`/`area_code` on the 281 Protocol Questions resolves against `seed-usoap-vocabularies.sql`'s enum options, and the demo dataset's own `demo-doc-a10v3`/`demo-pq-*`/`demo-acapite-*` rows coexist without collision. One dangling citation in the source (an active link pointing at a soft-deleted `PQ 7.999`) was found and excluded during extraction.
- **The gateway `API_KEY` now ships enabled by default across the platform, and the quickstart warns loudly about it.** `compliance_flow`'s `.env.example`, `compliance_web`'s and `compliance_import`'s `.env.docker.example` now set a shared public placeholder value (`API_KEY`/`NODE_RED_API_KEY`/`IMPORT_API_KEY`) instead of shipping empty — a cloned/demo stack is no longer an open gateway by default, though the placeholder itself must still be rotated before any real deployment (documented in the runbook's expanded §10). `demo-quickstart.sh` prints a loud "DEMO CREDENTIALS — DO NOT DEPLOY PUBLICLY" banner at the end of the run listing exactly what's still demo-only. Verified on a genuinely fresh instance: `isInstalled => true`, `user` row `1 admin` with `is_admin`, `/api/v1/App/user` → `401`.

(i) `docker compose exec` defaults to **root**, so `clear cache` / `sql diff --run` left root-owned files in `data/cache`; the web process then failed its next cache write and answered `500` on every API route, with nothing in the Apache log (the message is `file_put_contents(data/cache/listeners.json): Permission denied` in `data/logs/`). Every console invocation in the scripts, the README and the runbook now uses `-u www-data`. (ii) The preflight probed AtroCore *before* step 0b bootstrapped it — on a clean clone `web-data/` is empty, so Apache has no DocumentRoot and answers `404`, and Node-RED's `/specialties` answers `400` because it proxies to AtroCore. The independent services are probed first and AtroCore, its schema and Node-RED are checked after step 0b. (iii) Step 0b installed the metadata but never installed the application, so the schema and the admin user were still missing; it now runs `install-atrocore.sh` between the bootstrap and the metadata install.

- **A clean clone could not start AtroCore at all: the application is now bootstrapped into `web-data/`.** `docker-compose.yaml` bind-mounts `./web-data:/var/www/`, and a bind mount does not inherit the image's contents — so the AtroCore app that `prepare-pim.sh` installs during the image build was hidden behind an empty host directory. On a fresh checkout `atro-web` therefore started with a DocumentRoot that did not exist, `http://localhost` served nothing, and `install-metadata.sh` aborted with *"Start the stack first (docker compose up -d --build) so AtroCore creates web-data/"* — advice the stack cannot satisfy, because it is the bind mount that prevents it. It was a named volume (`web-data:/var/www/`, which Docker *does* populate from the image) until commit `25affed` replaced it. New `scripts/bootstrap-web-data.sh` copies the image's `/var/www` into `./web-data/` once, idempotently (`--force` to re-copy); `install-metadata.sh` calls it automatically when `web-data/<domain>/` is missing, the `Makefile` exposes `make bootstrap`, and §5.1/§7.2 of the runbook document it. Verified: mounting an empty directory at `/var/www` hides the app while the unmounted image contains it, the copy step produces a complete tree (`localhost/public/index.php`, `localhost/data`) with the image's `www-data` ownership, and the script's idempotent branch is a no-op on the existing tree.
- **`install-metadata.sh` failed on Docker Desktop/Colima-style hosts when it had to write `config.php` through a container.** The script stages a temp copy of `config.php` (owned by `www-data`, so the host user cannot write it in place) and used `mktemp`, which lands in `/tmp` — a path that is not shared with the Docker daemon on those setups. Bind-mounting it gave the container an empty *directory* at `/tmp/config.php`, so `cp` reported `can't stat 'web-data/<domain>/data/config.php/config.php': Not a directory` and the install exited non-zero *after* copying the metadata. The temp copy now lives in the repository root (writable by the host user, and already mounted into the container as `/repo`), so it needs no extra bind mount at all; `.config.php.*` is gitignored against a crash leaving it behind.
