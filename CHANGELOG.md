# Changelog

All notable changes to this project are documented in this file.

The format is inspired by Keep a Changelog and releases are dated — see CONTRIBUTING.md, "Versioning and releases".

## [Unreleased]

### Changed

- **The demo quickstart now derives every payload date from the seeded site visit, instead of importing the dates frozen into the tracked ZIPs.** The seed computes the site visit's window relative to the day it runs (`CURRENT_DATE + 21`/`+ 22`, §1 of `sql/seed-demo-dataset.sql`), while a ZIP committed to `compliance_import` freezes its dates the day it is written — so the demo drifted within a day of the payloads being built, and the drift was not cosmetic: the canonical import copies `checklist.startDate`/`endDate` onto the Alfresco inspection folder, which is the only place an inspection's window lives (`inspection` in AtroCore has no date columns), so a stale payload dated the inspection into the wrong week and its checklist items fell out of the year-filtered provider-history report. The quickstart now reads the window back from the seeded `site_visit` row (id `demo-sv-01`, `DEMO_SITE_VISIT_ID` overrides it), stamps a scratch copy of each of the three payloads with it via `compliance_import/scripts/stamp-payload-window.py`, imports the stamped copies (the tracked ZIPs stay pristine templates), and **step 6 now fails unless each inspection folder carries exactly the seeded window** rather than merely some window. The stamping is a no-op when re-run on the same window, so the quickstart stays idempotent. Verified live: the seeded window `2026-10-07 → 2026-10-08` is what both `AV-ZZZZ-A-0001` and `AV-ZZZZ-I-0001` now carry (the ATS payload's template window was `2026-10-06 → 2026-10-07`), with its findings re-dated to `2026-10-08` and the follow-up to `2026-10-21`.

### Added

- **The demo quickstart now imports both seeded inspections and fails if either has no window.** The dataset seeds two inspections (ATS `AV-ZZZZ-A-0001` and MET `AV-ZZZZ-I-0001`) but the quickstart only imported a payload for the ATS one, so the MET inspection had no canonical documents — and therefore no inspection folder, which is where the window lives (`vso:startDate`/`vso:endDate`; AtroCore's `inspection` table has no date columns). Its checklist items could never be dated and dropped out of the year-filtered provider-history report. New steps **2b/3b** post `compliance_import`'s `example data/demo_met_inspection_payload.zip` and run the canonical import for `AV-ZZZZ-I-0001`, and step 6 now reads both inspection folders back and **fails** unless each carries a window. Verified end to end: `AV-ZZZZ-A-0001 window: 2026-10-06 → 2026-10-07`, `AV-ZZZZ-I-0001 window: 2026-10-07 → 2026-10-08`, smoke 15/15, envelope audit 5/5. **Superseded (2026-09-16):** those were the payloads' template dates; both folders now carry the seeded site visit's window — see *Changed* above.
- **The model is now enforced, not merely tracked.** Three guards close the gap that let 19 entities go missing in the first place. `scripts/validate-metadata.py` asserts the exact expected entity set (32 names, `EXPECTED_ENTITIES`) and that every entity has a client definition, a scope and a layout directory with no orphans in any of the four trees; `KNOWN_UPSTREAM_ENTITIES` shrank from eleven entries to the one real upstream entity (`User`), because it had been an escape hatch — deleting `Location.json` used to pass, since `Location` was listed as "upstream". New `scripts/export-instance-metadata.py` (`make metadata-drift` / `make metadata-export`) compares the running instance's definitions against the repository and exits non-zero on any difference — the guard against the admin-UI edit that caused all of this — and copies them back when the instance is the source. And CI's `blank_instance_check` became **`validate:fresh-install`**: it deletes `web-data/` and `db-data/`, builds, bootstraps the application out of the image, installs the tracked model, runs `clear cache` + `sql diff --run`, runs all three seeds, and asserts the result (1 demo location / 2 providers / 3 inspectors / 2 inspections, 16 specialties, 7 vocabularies, 5 operational tables) plus the backup path. The job it replaces asserted only that PostgreSQL answered and a dump could be written — and passed for the entire period in which a clean clone could not build its application or its schema at all. Verified locally: the validator passes on the current tree and fails with the expected messages when an `entityDefs` or `clientDefs` file is hidden; the drift check reports "OK: metadata/ matches the running instance" and fails after a deliberate edit.
- **The whole operational model is now tracked, so a bare clone builds the schema — the dump is no longer needed for that.** The repository tracked 13 of the 32 entity definitions the running instance has (and 6/32 `clientDefs`, 6/32 `scopes`, 7/33 layout directories), under the assumption recorded in `metadata/README.md` that "only the files this project actually customises are tracked here". The other 19 — `Location`, `ServiceProvider`, `SiteVisit`, `Inspector`, `Finding`, the `CorrectiveAction*` family, `Inspected*`, `Person`, `Reglamento`, `DocumentoOACI`, `InspectionSchedule`, `ServiceArea`, `ActingInspector`, `CorrectiveActionFollowUp`, `CorrectiveActionPlan`, `FindingSeverity` — existed only in the gitignored `web-data/` tree and in the `atrocore.dump` purged in P0, so a fresh install created an application whose schema lacked all of them and whose first seed died with `relation "public.service_area" does not exist`. Eight of the *already-tracked* definitions link into them (`AcapiteOACI`→`DocumentoOACI`; `Inspection`→`InspectedProvider`/`InspectedService`/`InspectedSpecialty`/`InspectionSchedule`/`Location`; `InspectionCadence`, `InspectionQuestion`, `Normativa`, `Specialty` likewise), so the tracked subset could not even load on its own. `FindingSeverity` has no entity links but is queried live by `compliance_web`'s `server/findings/severityDeadlines.cjs`. Recovered from a provisioned instance (2026-09-16) after confirming every already-tracked file was already JSON-identical to its runtime counterpart, and that no recovered file carries environment-specific content (no paths, hosts, URLs or credentials — the definitions are `fields`/`links`/`indexes`/`collection` only). Metadata grows 51 → 220 JSON files and 13 → 32 entity definitions; the stale `ProtocolQuestion` layout directory is deliberately not copied, since `install-metadata.sh` removes it. **Verified on an isolated fresh instance** (own compose project, network and port; empty `web-data`/`db-data`; pinned 2.1.6 image): bootstrap → `install-metadata.sh` → `sql diff --run` creates the operational tables and **all three seeds pass**, the demo dataset landing 1 location / 2 providers / 3 inspectors / 1 site visit / 2 inspections / 9 questions / 16 specialties. The runbook, README and the quickstart's schema guard were updated in the same change, because they previously sent anyone with a missing schema to restore a dump — which is no longer the remedy.
- **`demo-quickstart.sh` now checks that the operational schema exists before it seeds, and the First-5-Minutes path restores the dump first.** A clean clone has no operational schema to build from: the tracked `metadata/` tree is a partial overlay (13 of the running instance's 32 `entityDefs` — see `metadata/README.md`), so `location`, `service_provider`, `site_visit`, `service_area`, `finding` and the rest come from a provisioned `atrocore.dump`, not from the repository. Restoring it is now step 5 of the README checklist (before the metadata install), the synthetic-dataset section says it loads *on top of* a provisioned instance, runbook §7.2 carries the same warning, and the quickstart's preflight probes `public.service_area` and stops with the exact restore command instead of failing four steps later inside a seed script (`SCHEMA_PROBE_TABLE` overrides the probe so the failure path can be exercised deliberately). Reproduced on an isolated fresh instance: without the dump the app serves after bootstrap but `seed-usoap-vocabularies.sh` fails with `column "multilingual" of relation "extensible_enum" does not exist` and `seed-demo-dataset.sh` with `relation "public.service_area" does not exist`. The underlying metadata gap is scheduled as **P2.6** in `TECHNICAL_DEBT_ANALYSIS.md`. **Superseded on 2026-09-16** by the entry above: the model is tracked, so the guard now reports a schema that has not been synced rather than a missing dump, and its message says so.
- **The compliance integration runbook and its executable demo quickstart now live in this repository.** `docs/COMPLIANCE_INTEGRATION_RUNBOOK.md` (previously at the workspace root, outside every repository and therefore unversioned) and `scripts/demo-quickstart.sh` (re-rooted here) moved into the repository a newcomer has to start from. The script takes a running stack to the seeded demo dataset, the demo identities, the imported work products and the read-only verification in one additive, idempotent pass, then prints the closure-review calls it deliberately leaves to a human; §7 of the runbook remains the step-by-step version and §7.7 the traps. Every other repository's README now links to §7, so the sequence is documented once instead of per repository. Verified by running the moved script from its new home (`--skip-seed --skip-import`) and by re-reading the runbook's relative references.
- **The demo dataset now includes a checklist catalog and its USOAP citation chain.** Three topics and nine questions across the demo specialties (`ATS-9001…9003`, `NAV-…`, `MET-…` — the `9xxx` range, because `code` is unique per `(code, deleted)` and the low ranges are taken by the operational catalog), each cited through `Normativa → AcapiteOACI → UsoapProtocolQuestion` with synthetic `PQ 99.x` codes (the entity's own pattern requires `PQ N.NNN`, and ICAO does not assign 99.x). It also seeds `InspectionQuestion`, the per-inspection selection `/checklist` actually queries — the master catalog alone is invisible to the app. Verified against the running stack: `/checklist` now returns the three ATS questions with the topic, verification, guidance, `reglamento`/`articulo`/`texto`, ICAO reference and a resolved `usoapPqReference` (`CE-5`, `PQ 99.001`), and `riskLevel` resolving to `Medium`/`Low`/`High` — all labels coming from the vocabulary seed. Dataset grows from 38 to 82 rows over 25 tables; `--remove` still deletes exactly the `demo-` rows.
- **A committed seed for the risk / USOAP extensible-enum vocabularies.** `ChecklistQuestion.riskLevel`, `UsoapProtocolQuestion.criticalElement` and `.areaCode`, `UsoapEvidenceExpectation.artifactCategory` and `InspectionQuestion.compliance` are `extensibleEnum` fields whose vocabularies the **tracked** entity definitions reference by hard-coded id — and AtroCore's extensible enums have no home in `metadata/` (`install-metadata.sh` syncs entityDefs, clientDefs, scopes and layouts only). So they existed *only in the database*, and a fresh install could not resolve a single risk level or USOAP Critical Element / area: `/checklist` renders `riskLevelName`/`criticalElementName`/`areaCodeName` through these enums, and `POST /api/usoap/ce-evidence-report` groups by them. `sql/seed-usoap-vocabularies.sql` + `scripts/seed-usoap-vocabularies.sh` (`make db-seed-vocabularies YES=1`) create the 5 enums and their 42 option bindings with the canonical ids, so no existing record is orphaned. Additive (`INSERT ... ON CONFLICT DO NOTHING`) and deliberately **not** removed by `seed-demo-dataset.sh --remove`. Verified by deleting all five enums inside a transaction and re-running the seed — 0 → 5 enums / 42 bindings, then rolled back with the live data untouched. `scripts/validate-seeds.py` (the `validate:seed` CI job) cross-checks the seed against the enum ids the entity definitions reference, which is how the two enums I had missed (`usoapArtifactCategory`, `compliance`) were caught. **Extended 2026-09-16** to 7 enums / 47 bindings: tracking the operational model brought in two more `extensibleEnum` fields (`ActingInspector.role` → `inspectorRoles`, `Finding.class` → `findingClass`), and `validate-seeds.py` failed the build until they were seeded — which is exactly the check working as intended.
- **`scripts/validate-seeds.py` replaces `scripts/validate-demo-seed.py`** and now covers both seed files: the demo dataset's additive-only invariants plus the vocabulary id contract.

- `metadata/` as the version-controlled source of truth for AtroCore entity metadata, with `scripts/install-metadata.sh` to install it into the gitignored `web-data/` runtime tree.
- `ActivityType` reference entity (oversight activity type: `A` Auditoría, `I` Inspección, `M` Monitoreo, `D` Revisión documental, `S` Análisis de suceso).

- **A committed synthetic demo dataset, so a fresh clone is no longer empty.** Every operational record (locations, providers, inspectors, site visits, inspections) existed only inside the binary `atrocore.dump`/`db-dumps/*.dump` files, which are gitignored and were purged from history in the P0 secret cleanup — so `git clone` + `docker compose up` produced an app with nothing to click. `sql/seed-demo-dataset.sql` + `scripts/seed-demo-dataset.sh` add one fictional airport (ICAO `ZZZZ`, ICAO's own "unknown aerodrome" placeholder, so generated codes are obviously synthetic), two service providers, three inspectors, their services and specialties, a site visit three weeks ahead of the day you seed, two inspections and the interview schedules the plan generator requires. Everything is invented (`.invalid` e-mail addresses, `Demo …` names), contains no credentials, and is **additive**: it only ever writes rows whose `id` starts with `demo-`, so it is safe against a database that already holds real records. `--remove` deletes exactly those rows. `make db-seed-demo YES=1` / `make db-seed-demo-remove YES=1`. The visit is seeded as `Planned` because `/siteVisits` hides visits that are still `Created`. Verified live: 38 rows created, 0 left after `--remove`, 38 after re-seeding, and `/siteVisits`, `/providers?siteVisit=`, `/location` and `/inspectors?specialty=` all return the demo records while the existing smoke harness stays 15/15.
- **`demo_seed_check` replaced by `validate:seed`, which actually runs.** The old job skipped itself whenever `atrocore.dump` was absent — and since dumps are gitignored, that was every run — then asserted only that "some public tables exist", which was already true against an empty database. It cannot be fixed by removing the skip: the `atro-web` image this pipeline builds starts Apache with a DocumentRoot that does not exist (the AtroCore application is never installed), so no schema is ever created and there is nothing to seed. The job is therefore replaced by `scripts/validate-demo-seed.py`, which runs in a `python:3.12-alpine` container with no Docker at all and enforces the invariants a database would otherwise only catch late: additive-only (every `DELETE` scoped to `demo-` rows), no `TRUNCATE`, every row id namespaced, the row count matching its documentation (38), and `--remove` covering every table the seed writes. Both new failure modes are verified to trip. **Open CI gap, reported rather than papered over:** the pipeline never brings up a working AtroCore, so nothing in CI exercises the metadata install or the schema sync end to end.

### Fixed

- **A fresh clone's AtroCore was scaffolded but never *installed*, so every API call answered `500`.** `docker compose up -d --build` builds the application files; it does not run AtroCore's installation. A fresh instance therefore had `'isInstalled' => false` in `data/config.php` and an empty `user` table, so `/api/v1/App/user` answered `500` with an empty body, `compliance_flow`'s `/specialties` answered `400`, and `compliance_web` login could not work — the platform was unusable however green the seeds were. New `scripts/install-atrocore.sh` drives AtroCore's own web wizard (`POST /api/v1/Installer/setLanguage`, then `/createAdmin`) non-interactively, with the credentials the platform already uses (`ATROCORE_USERNAME`/`ATROCORE_PASSWORD` in `compliance_flow/.env`), so the super admin is the account Node-RED authenticates as. Two non-obvious things it encodes: the installer API path is `/api/v1/Installer/<action>` — **not** the usual `/api/v1/<Controller>/action/<action>`, and `Application::runInstallerApi()` swallows every `Throwable` into a bodiless `500`, so a wrong path is indistinguishable from a real failure; and `createAdmin` calls `Installer::prepareDataBase()`, which **drops every table** and rebuilds from the application's metadata, so the script refuses to run when the app already reports itself installed and requires `--yes`. Verified on a genuinely fresh instance: `isInstalled => true`, `user` row `1 admin` with `is_admin`, `/api/v1/App/user` → `401`.
- **Console commands now run as `www-data`, and the quickstart can finally run on a raw clone.** Three ordering/permission defects, all found by running the documented path against a freshly recreated database. (i) `docker compose exec` defaults to **root**, so `clear cache` / `sql diff --run` left root-owned files in `data/cache`; the web process then failed its next cache write and answered `500` on every API route, with nothing in the Apache log (the message is `file_put_contents(data/cache/listeners.json): Permission denied` in `data/logs/`). Every console invocation in the scripts, the README and the runbook now uses `-u www-data`. (ii) The preflight probed AtroCore *before* step 0b bootstrapped it — on a clean clone `web-data/` is empty, so Apache has no DocumentRoot and answers `404`, and Node-RED's `/specialties` answers `400` because it proxies to AtroCore. The independent services are probed first and AtroCore, its schema and Node-RED are checked after step 0b. (iii) Step 0b installed the metadata but never installed the application, so the schema and the admin user were still missing; it now runs `install-atrocore.sh` between the bootstrap and the metadata install.
- **The image build has been broken since 2026-08-07, and the application version was never pinned.** Both skeleton repositories moved that day ("Update atrocore/core version and rename installer files" — `skeleton-atrocore@af44164`, `skeleton-pim-no-demo@b350ca3`), renaming `composer.phar` to `atrocore-installer.phar`. `prepare-pim.sh` still ran `php composer.phar self-update && php composer.phar update`, so a clean build failed; and because `\Atro\Composer\PostUpdate::getRootPath()` locates the project root by walking up until it finds a directory containing `composer.phar`, driving the new installer also failed with `Failed! Can't find root directory.` The build now pins each skeleton revision per variant, downloads Composer itself (2.8.12, sha256-verified — it satisfies that marker and remains a fallback tool), and lets the AtroCore installer drive the install. The installer is required, not merely preferred: the public package listing (`packagist.atrocore.com/packages.json`, 53 packages) carries `atrocore/core`, `export` and `import` but omits `atrocore/atrocore-legacy` and `atrocore/slim`, which `core` requires — plain `composer update` resolves neither. `COMPOSER_IPRESOLVE=4` works around the builder resolving `repo.packagist.org` to IPv6 and being unable to route it, and `first_update.log` is removed so `PostUpdate::uploadDemoData()` does not pull AtroCore's own demo dataset over this project's.
- **The application version is now pinned — which is what made the vocabulary seed fail on a fresh install.** The skeleton's `composer.json` floats (`atrocore/core >=2.3.12`, `export`/`import` `*`) and the build ran `update`, so the installed app, and therefore the database schema, changed with wall-clock time: the running instance was `atrocore-legacy 1.1.11` / core `2.0.23`, while a fresh build pulled `1.2.12` / core `>=2.2.30`. `ExtensibleEnum.json` lost its `multilingual` field somewhere between core 2.1.6 and that line, so `seed-usoap-vocabularies.sh` died with `column "multilingual" of relation "extensible_enum" does not exist` on a clean install while working on the long-lived instance. New `.docker/php/scripts/composer.pinned.json` pins `atrocore/core 2.1.6`, `atrocore/export 1.10.1`, `export-http 1.8.0`, `import 1.10.2`, `import-http 1.6.1` — the top of the range this repository itself declared (`>=2.0.23 <=2.1.6`) — against the public repository, with no account id and with Composer's security-advisory blocking left **on** (pinning the exact 1.1.11 set would have required disabling it, because `phpspreadsheet 1.16.0` carries published advisories; 2.1.6 resolves `1.30.6`). Verified on an isolated fresh instance: the image builds, the app serves, `extensible_enum` has `multilingual`, and `seed-usoap-vocabularies.sh` + `seed-nomenclatura.sh` both succeed. The demo dataset still needs the operational model, which remains P2.6 in `TECHNICAL_DEBT_ANALYSIS.md`.
- **A clean clone could not start AtroCore at all: the application is now bootstrapped into `web-data/`.** `docker-compose.yaml` bind-mounts `./web-data:/var/www/`, and a bind mount does not inherit the image's contents — so the AtroCore app that `prepare-pim.sh` installs during the image build was hidden behind an empty host directory. On a fresh checkout `atro-web` therefore started with a DocumentRoot that did not exist, `http://localhost` served nothing, and `install-metadata.sh` aborted with *"Start the stack first (docker compose up -d --build) so AtroCore creates web-data/"* — advice the stack cannot satisfy, because it is the bind mount that prevents it. It was a named volume (`web-data:/var/www/`, which Docker *does* populate from the image) until commit `25affed` replaced it. New `scripts/bootstrap-web-data.sh` copies the image's `/var/www` into `./web-data/` once, idempotently (`--force` to re-copy); `install-metadata.sh` calls it automatically when `web-data/<domain>/` is missing, the `Makefile` exposes `make bootstrap`, and §5.1/§7.2 of the runbook document it. Verified: mounting an empty directory at `/var/www` hides the app while the unmounted image contains it, the copy step produces a complete tree (`localhost/public/index.php`, `localhost/data`) with the image's `www-data` ownership, and the script's idempotent branch is a no-op on the existing tree.
- **`install-metadata.sh` failed on Docker Desktop/Colima-style hosts when it had to write `config.php` through a container.** The script stages a temp copy of `config.php` (owned by `www-data`, so the host user cannot write it in place) and used `mktemp`, which lands in `/tmp` — a path that is not shared with the Docker daemon on those setups. Bind-mounting it gave the container an empty *directory* at `/tmp/config.php`, so `cp` reported `can't stat 'web-data/<domain>/data/config.php/config.php': Not a directory` and the install exited non-zero *after* copying the metadata. The temp copy now lives in the repository root (writable by the host user, and already mounted into the container as `/repo`), so it needs no extra bind mount at all; `.config.php.*` is gitignored against a crash leaving it behind.
- Skip ACL restoration during `pg_restore` to avoid missing-role grant failures. (`ad0513f`)
- Skip object ownership restoration during `pg_restore` to avoid missing-role ownership errors. (`db18d3f`)
- Install `bash` in the GitLab CI Alpine image to prevent shell-related job failures. (`380ab53`)
- Wait for PostgreSQL readiness in GitLab CI jobs before running checks. (`4580a6f`)
